# 移动底盘的控制

> 本文是 grasp_grape 的理论笔记之一。每一节末尾的「在本项目里」给出它在这套代码里
> 的落点和踩过的坑。

---

## 1. 滑移转向的运动学

四轮滑移转向（skid steer）没有转向机构，靠左右两侧轮速差实现转向。给定期望的
前进速度 `v` 和角速度 `ω`，左右轮线速度是

```
v_left  = v − ω · b/2
v_right = v + ω · b/2        b = 轮距
```

它有两个绕不开的性质：

- **转向必然伴随轮胎侧向刮擦**。这是它在软土上牵引好、结构简单的代价，也是为什么
  它的里程计特别不可信。
- **`v` 和 `ω` 通过同一组轮子耦合**。这一点会以很不直观的方式咬人，见第 4 节。

> **在本项目里**：轮距 0.64 m，轮径 0.32 m，驱动扭矩上限 900 N·m/轮。
> 扭矩留了很大余量不是为了加速——802 kg 在 0.5 m/s² 下总共只要约 55 N·m——
> 而是因为**滑移转向的每一次转弯都要把四条轮胎横向刮过地面**，余量都花在这里。

---

## 2. 为什么轮式里程计在这里不能用

滑移转向的轮速与实际位移之间没有可靠关系（刮擦、打滑、土块）。因此本项目的
`world_tf.py` 采用了和 AMCL 相同的结构：

```
world ──(修正)──> odom ──(轮式里程计)──> base_footprint
         ↑                    ↑
    由外部定位提供        由驱动插件发布，会漂
```

**关键点：不去改 `odom → base_footprint`，而是修正它上面那一层。** 这样做的好处是
下游（MoveIt 在 `world` 系里规划）拿到的是准确的位姿，而里程计本身保持连续、
不跳变——跳变的位姿会让局部控制器发疯。

> **在本项目里**：`world_tf.py` 目前用 Gazebo 真值充当那个"外部定位"，它是
> **VINS-Mono 的占位节点**。换成 VIO 输出时下游一行都不用改——这正是选择修正
> odom 上层而不是伪造 odom 的意义。

## 3. 车道保持：从横向误差到转向指令

沿直线行驶的任务可以分解成两个误差：

- **横向误差** `e_y` —— 离目标车道中心线的距离
- **航向误差** `e_θ` —— 车头方向与车道方向的夹角

### ❌ 一个看起来自然、实际有陷阱的写法

```
ω = −K_cross · e_y + K_yaw · e_θ
```

两项相加，各自把一个误差往零推。问题是：**它有一个稳定的偏置平衡点。**

当 `K_cross · e_y = K_yaw · e_θ` 时，`ω = 0`，控制器"满意"了，但车其实**既偏离
车道、又斜着车头**，并且会保持这个姿态一路开下去。

> **在本项目里**：实测抓到过这个平衡点——横向偏 0.256 m、航向偏 11°，两项正好抵消，
> 车就那样斜着开，最后骑到葡萄行上，横向偏差累积到 0.92 m 卡死。

### ✅ 纯追踪式（pure-pursuit 风格）

不要把横向误差直接变成转向量，而是把它变成一个**瞄准航向**：

```
θ_aim = θ_lane − arctan(K_look · e_y)      （限幅）
ω     = K_yaw · (θ_aim − θ)
```

现在只有一个误差要调零。横向偏得越多，瞄得越"斜"，车自然拐回车道；回到车道上时
`θ_aim` 自动变回车道方向。**偏置平衡点不存在了**，因为 `ω = 0` 当且仅当车头正对
瞄准方向，而瞄准方向只有在横向误差为零时才是车道方向。

## 4. 比例控制的末端塌陷（本项目最隐蔽的一个 bug）

纯比例的接近律 `v = K · d`（`d` 是到目标的剩余距离）有个致命的实际问题：
**越接近目标，指令越小**。而转向分量的大小并不同步缩小。

在滑移转向上，这会导致：

```
剩余 0.06 m  →  v = 0.9 × 0.06 = 0.054 m/s
航向差 5.3°  →  ω = −0.19 rad/s
                 v_left  = 0.054 + 0.061 = +0.115 m/s
                 v_right = 0.054 − 0.061 = −0.007 m/s   ← 内侧轮被抵消到零
```

净前进速度归零。**车在原地打转，永远走不完最后那几厘米。**

> **在本项目里**：这就是"底盘间歇性卡死"的真相，一直被误判成"被障碍物卡住"。
> 诊断的关键是在超时路径上打印**轮速**：
> ```
> wheel_fl +0.72 rad/s     wheel_fr +0.00 rad/s
> wheel_rl +0.72 rad/s     wheel_rr +0.00 rad/s
> ```
> 左轮转、右轮完全不转——这不是被卡住，这是被指令成了原地转向。
>
> **区分"轮子在转但车不动"和"轮子根本没转"是这类问题的第一个分叉点**，
> 而这需要在诊断里同时打印指令、真值速度和轮速。

两条修正：

1. **接近段速度下限**：`|v| < V_min` 时抬到 `V_min`，让它真的能走完最后一段。
2. **转向指令上限跟着线速度走**：`|ω| ≤ |v| / (b/2)`，保证只要还有距离要走，
   转向量就不会大到把内侧轮反转。原地转向仍然允许，那是另一个函数（`face_heading`）
   的事。

## 5. 到位判据：不要要求做不到的事

一个直觉上"更严谨"的到位判据是同时要求纵向到位**和**横向对正：

```
if |y − y_target| < tol_y and |x − x_lane| < tol_x:   # ← 有陷阱
```

**滑移转向不能横移。** 消除横向误差必须沿着车道来回走，而一走 `y` 就偏，判据又
因为 `y` 不满足而拒绝——两个条件互相排斥，控制器绕圈到超时。

> **在本项目里**实测抓到过这个状态：`y` 精确到达目标（−1.07 对 −1.07），
> 横向偏 0.311 m，航向 124.4°——**而 124.4° 正好是控制器为该横向误差算出的瞄准
> 航向**，也就是说控制环已经收敛，只是收敛到了判据不接受的地方。
>
> 改成只判 `y`，横向误差改为**上报并告警**。它到底要不要紧，交给真正的关口去判：
> 机械臂的 `reachable()` 用臂基座到果实的真实三维距离决定这一停位能不能干活。
> **判据应该落在真正的约束上，而不是落在一个代理量上。**

## 6. 单目 VIO 在地面车上的固有困难

视觉惯性里程计（如 VINS-Mono）初始化时必须估计出**重力方向**和**尺度**。这两件事
都依赖于加速度激励——IMU 只有在加速度变化时才能把重力和运动加速度区分开。

而一台匀速爬行的地面平台，加速度方差接近零。

> **在本项目里**：实测开了 7.6 m，VINS-Mono 一直报 `IMU excitation not enouth`。
> 加入一段前后加速脉冲（`drive.py: excite()`，4 组）之后**立刻**
> `Initialization finish!`。
>
> 这不是仿真里的取巧——跑单目 VIO 的地面机器人在实际部署里就是要先这么晃一下，
> 或者被推一下。**平面匀速运动对单目 VIO 是退化工况**，这是方法本身的性质。

即便初始化成功，地面车对单目 VIO 仍然不友好：运动近似平面、场景（果园）高度重复、
尺度容易漂。本项目目前的状态是能初始化但随后发散，仍在路线图上。

---

## 7. 控制能力反过来约束任务设计

一个容易被忽略的方向：**底盘能做到什么精度，决定了机械臂的任务怎么安排。**

> 本项目的臂可达包络约 1.35 m，贴垄站距 0.80 m 时，够到 1.7 m 高的果串需要 1.25 m，
> 余量只有约 0.07 m。这意味着：
>
> - 横向误差**直接从余量里扣**，0.1 m 的车道偏差就吃掉大半余量
> - 沿垄方向偏离正对位置 0.2 m 也基本出界
>
> 所以作业策略必须是**每串停一次车**，而不是每块板停一次——这不是效率选择，
> 是被可达性算出来的硬约束。规划、控制、任务安排在这里是一件事。
